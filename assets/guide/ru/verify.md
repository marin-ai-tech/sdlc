# Доказательства проверки

Гейт проверки проходит по записанным доказательствам, а не по словам агента.

```bash
sdlc verify --change add-export           # запускает все проверки из verify.commands и verify.mcp
sdlc verify --list                        # настроенные проверки
sdlc verify --check --change add-export   # сценарии спецификации без поведенческих доказательств
```

## Что записывается

- Буквальный вывод каждой команды в `verification.md`, с кодом выхода и длительностью.
- Отпечаток рабочего дерева. Коммит сохраняет доказательства свежими; изменение кода делает их устаревшими, и гейт
  ждёт нового запуска.
- MCP-проверки (`verify.mcp`): CLI сам вызывает инструмент MCP-сервера команды (например, «зелёный ли CI для этого
  коммита?») и записывает ответ.

## Что ещё говорят доказательства

- Файлы из раздела плана «Files that change», которые никто не тронул, выводятся предупреждением.
- `## Not run / limits` в `verification.md`: что не запускали и почему (заполняет тестировщик).
- Файлы из папки `verification/` изменения (скриншоты, результаты браузерных проверок) перечисляются ссылками.

## Если проверка упала

Исправляйте код, а не тест, и запустите `sdlc verify` снова. Упавшая обязательная проверка проваливает гейт.
При исправлении ошибки тесты заблокированы (`sdlc guide bugfix`).

## Проверки не настроены

`sdlc verify` откажет. Добавьте команды сборки, тестов и линтера проекта в `verify.commands` в `openspec/sdlc.yaml`
(этот файл правит человек) или пусть их предложит `sdlc adopt`.

## Результаты вне сессии

Когда человек или CI запускает `sdlc verify` вне сессии агента, MCP-результаты ещё и ждут во входящих. Агент увидит их
при следующем старте сессии:

```bash
sdlc inbox list
sdlc inbox done <id>
```
