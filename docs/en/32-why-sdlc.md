# Why work with sdlc

This page is for a team deciding whether to adopt sdlc. It covers what sdlc costs to run, why it stays simple, and
why it lives in the console. It ends with a real case: what happened when the gates were skipped.

## Almost nothing to deploy

sdlc needs only what a development team already has:

- Node.js 20.19 or later and git;
- the coding agent the team already uses (six tools are supported);
- one package from the GitHub release, installed with one command.

There is nothing to host:

- no server, database or container;
- no cloud account, and no service to sign in to.

The state lives in the repository as plain files: the backlog, the approvals, the evidence and an append-only log.
The audit, the report and the dashboard are built from those files and work offline. Removing sdlc is just as
cheap: `sdlc uninstall` removes the generated files, and the OpenSpec folder stays a plain OpenSpec project.

```bash
npm install -g https://github.com/marin-ai-tech/sdlc/releases/latest/download/sdlc.tgz
sdlc init
```

Do not run `npm install -g sdlc`: the registry package of that name is unrelated.

## Simple by design

- **One command to start.** `sdlc init` asks a few questions and writes the hooks, workflows and settings for the
  chosen tools; `sdlc doctor` checks the result.
- **One question at every step.** `sdlc next` names the next step, or the person who must act and the exact command.
  Nobody has to remember the process.
- **Files you can read.** Settings, roles and the backlog are short YAML and Markdown files under `openspec/`. A
  change is a folder with its intent, spec, plan, tasks and review.
- **The same process in every tool.** A team can mix tools and keep the same gates and workflows. OpenCode has no
  stop check; [the architecture page](04-architecture.md) lists such differences.

## Console first

Every part of sdlc is a command:

- **Decisions are commands in a person's own terminal.** `sdlc approve`, `sdlc reject` and `sdlc waive` run under
  the person's git identity, and the CLI refuses them inside an agent session. With `signing: required` in
  `roles.yaml`, each approval must arrive in a signed commit; see [roles and signing](08-roles-and-signing.md).
- **Every read has `--json`.** Agents, scripts and CI read the same state that people see.
- **It runs wherever a terminal runs.** A laptop, a server over SSH and a CI job behave the same way.
- **No separate interface to learn.** The task board is a command too, and the report and the offline dashboard
  are generated by commands.

## What skipping the rules cost

In one of our releases, six changes were shipped as a single batch. There were no acceptance tests written first and
no separate task per change. There was no review before the release. The gates were approved after the fact, against
a description of code that had already shipped.

The review held afterwards found:

| What | Count |
|---|---|
| Changes in the batch | 6 |
| Files in one commit | 56 |
| Important findings | 18 |
| Of them, security findings | 2 |
| Minor findings | 26 |

Some examples of the important findings:

- an agent could switch off the check that blocks its stop until verification passes;
- cleanup after a timed-out check could signal an unrelated process that had reused an id;
- a project opened through a linked folder could not approve anything;
- a file with a git filter could never be approved;
- a verification that failed for a missing fingerprint told the user to fix the code.

The fix took more work than the batch saved:

- a fix right after the release, when a CI run on another platform found surviving processes;
- three follow-up changes, one of them in three parts;
- each follow-up went through the full process: an acceptance test first, a review, a second engineer's approval.

Each rule that was skipped targets one kind of these defects:

| Skipped rule | What it can catch |
|---|---|
| An acceptance test written before the code | the stated behaviour failing in the edge cases, such as linked folders and git filters |
| A spec approved by a second person | edge cases left unnamed before any code is written |
| One change per task | a review covers one change, not 56 files at once |
| Review before release | the findings reach the team, not the users |

Changes made by the rules also get review findings. The difference is where the findings surface. With the gates,
review finds them before the release. Without them, the defects ship, and every fix pays for the whole cycle
again.
